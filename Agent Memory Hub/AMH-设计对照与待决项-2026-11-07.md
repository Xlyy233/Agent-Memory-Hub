## 一、结论摘要

1. **两份文档不是竞争关系，是上下游。** 说明书定方向和愿景；Phase 0 报告把其中每条「计划」拿去和本机事实核对，收紧成「已验证 / 推测 / 待确认 / 建议」。Codex 回应基本全盘认同说明书架构，但把安全边界、Provider 契约、Git 增量细节写成了可直接实现的规格。
2. **4 个待统一点，Codex 全部认同方向，但修正了 3 处。** 状态机从「两维」升级为「四维」；工作记忆不接管是对的，但我给的理由不成立；证据门槛从「存在 sources」改为「来源支持该主张」。
3. **合并后的 Phase 1 定位被升级：** 不是「能存取记忆」，而是「**能按来源证明、按批准版本检索、按项目隔离，并在未获授权时阻断外发**」。调度、多 Agent 实际接入、自动 Loop 继续留在后续授权范围。

## 二、四个待统一点与 Codex 回应

### 1. 记忆状态机

**原分歧：** 说明书写 `candidate / verified / stale / archived`；报告写 `candidate → approved/rejected → superseded/revoked` + 哈希变更触发复核。核心问题：`verified` 是「有证据」还是「人工批准」？

**Codex 结论：认同拆分，并补充有效性维度。** `verified` 不宜同时表示「有证据」和「人工批准」，建议改为四个独立维度：

| 维度 | 回答的问题 | 示例取值 |
| --- | --- | --- |
| 证据与验证结果 | 什么证据支持，实际核查了什么？ | 用户明确确认、静态核对、运行验证；通过/失败/未执行 |
| 审核状态 | 是否允许作为正式记忆使用？ | `pending` / `approved` / `rejected` |
| 有效性 | 现在是否仍然适用？ | `current` / `stale` / `superseded` / `revoked` |
| 归档 | 是否退出日常使用？ | `archived` 标记或时间 |

并补充两条判据：

- **证据不宜简单排成高低等级。** 用户确认可以证明「选择了某种设计」，不能证明「程序运行正常」；测试通过也不能证明用户批准了某项产品决策。
- **会改变 Phase 1 验收标准。** 默认检索须同时满足：人工批准、证据满足该类型要求、内容哈希与批准版本一致、未过期或撤销、项目和适用范围匹配。`stale` 内容默认排除，可由显式历史查询返回；哈希变化应使旧批准失效并触发复核，仅检测到文件变化不能自动得出「新内容已被批准」。

**合并方案：** 采用四维模型；`approved` 只由人工确认产生；索引检索默认只返回 `approved + current + 未归档` 的内容。

### 2. 工作记忆归属

**原分歧：** 说明书把「当前任务状态 / 下一步工作」列为 Working Memory 由 AMH 管理；报告认为 Codex 已有任务约束机制，AMH 不接管任务状态。

**Codex 结论：认同首期不接管，但反对我的理由。** 我提出的「工作记忆频繁写入，与单写入者 + 人工审核冲突」不成立——单写入者可以处理频繁写入，人工审核也只约束长期记忆晋升、不约束临时任务状态。**真正的理由是：** AMH 一旦接管当前任务状态，就要处理恢复、并发任务、所有权、取消和跨 Agent 交接，容易与 Agent 自身状态产生**两个事实源**。Codex 同时承认，其 Phase 0 报告只确认了 Codex 已有任务约束及会话机制，**没有证明它能满足所有跨 Agent 工作记忆需求**——例如跨 Agent 接力可能需要共享任务快照，这是后续反例。

**Phase 1 边界建议：** 不拥有实时任务状态；可以接收用户选定的任务结论或交接快照，作为带时间的**候选资料**，不能据此自动恢复任务或继承授权。

**合并方案：** 采纳。工作记忆不进 Phase 1 主链路，但保留「任务结论/交接快照作为候选来源」的入口。

### 3. 路径与 Git

**原分歧：** 说明书目录写 `D:\AgentMemoryHub\` 且 Vault 用 Git 做版本管理；实际工作区是 `D:\Agent Memory Hub\`，Obsidian 建了同名嵌套 vault，且当前工作区未被识别为 Git 仓库。

**Codex 结论：认同纠正，建议先保留现有 Vault。**

- 项目根：`D:\Agent Memory Hub`
- Vault 根：`D:\Agent Memory Hub\Agent Memory Hub`
- Controller 代码与内部状态：放在项目根下、Vault 外，具体子目录在 Phase 1 设计时确定。

理由：优先减少迁移。现有嵌套名称虽不理想，但不值得在首期为整齐而移动笔记、修改 Obsidian 配置。说明书中的 `D:\AgentMemoryHub\` 应改为示例或逻辑路径，**不能成为硬编码**。

**必须区分两种 Git：**

- **来源仓库 Git：** EQDM 的提交 ID，用于定位来源。
- **记忆库 Git：** 记录已审核记忆的版本变化。

AMH 尚未初始化 Git，不影响引用 EQDM 已有提交。对未提交文件，使用「来源仓库 HEAD + 相对路径 + 工作区快照哈希」，明确标注草稿；非 Git 来源不强求 Commit ID。

**验收变化：** 允许 Commit ID 为空，但必须具备与来源类型匹配的定位信息和内容指纹。Vault 版本管理建议在正式记忆首次入库前建立；初始化及首次提交应列入后续实施方案，先明确范围、忽略规则及身份配置，**不在本轮执行，也不默认授权远端推送**。

**合并方案：** 采纳，项目根 / Vault 根 / 代码状态目录三分；Git 初始化列为 Phase 1 前置任务但需单独授权。

### 4. 阶段编号

**原分歧：** 说明书 Phase 4 才跨 Agent、Phase 3 异步调度；报告把调度明确暂缓、多 Agent/MCP/Loop 推到「另行评估」。

**Codex 结论：认同统一，建议按能力闭环编号：**

| 阶段 | 主要交付 |
| --- | --- |
| Phase 0 | 环境与现状审计 |
| Phase 1 | Agent 无关数据契约、离线采集审核检索闭环、文档入口 |
| Phase 2 | 经批准的云模型候选提取、Codex 接入验收 |
| Phase 3 | 异步调度、重试恢复、并发治理 |
| Phase 4 | 多 Agent 实际接入、自动开发 Loop 集成 |

跨 Agent 的数据兼容性从 Phase 1 开始，实际适配与自动化在后续阶段完成。

**Phase 1 明确不做（8 项）：** 真实云模型调用、自动外发、后台调度、Git Hook、实时任务状态管理、自动批准记忆、自动开发 Loop、修改 Agent 全局配置。

Codex 补充：这会调整阶段验收归属，但**不会提前授予后续操作权限**。

**合并方案：** 采用该编号，旧文档编号在实施方案中做映射。

## 三、三个判断与 Codex 回应

### A. 「公共 / 跨 Agent」是否后置 —— 认同，不冲突

「Agent 无关」应从第一天成立，包括项目命名空间、来源契约、状态语义和上下文输出格式；但它**不等于所有 Agent 可以访问所有项目、所有候选及所有敏感内容**。

纯文档入口可以提前到 Phase 1，内容只需说明四件事：

1. 从哪里检索；
2. 默认读取哪些已批准记忆；
3. 如何核对来源与适用范围；
4. 记忆不能替代当前指令或授予操作权限。

这与报告 2.4 节「不把整个 Vault 塞进全局规则」一致。

**授权区别：** 在 AMH 内提供供各 Agent 使用的入口文档，与**实际修改 Codex、Claude Code 等的全局配置是两项操作**。前者可纳入 Phase 1；后者仍须单独审批。

**验收变化：** 同一份正式记忆及其上下文输出不依赖 Codex 私有状态；入口文档可供不同 Agent 理解。尚不能据此宣称所有 Agent 已接入。

### B. sources 多态 —— 认同，但必须增加类型专属校验

仅用 Commit ID 和路径不够，建议支持 `git / command / file / user-statement / doc`，并允许一条记忆引用多个来源：

| 来源 | 最低核验信息 |
| --- | --- |
| git | 仓库标识、提交或快照、路径、内容哈希 |
| command | 准确命令、工作目录、执行时间、退出码、脱敏结果、环境标识 |
| file | 路径或稳定标识、内容哈希、必要元数据 |
| user-statement | 明确陈述、确认时间、对话引用、适用范围 |
| doc | 文档定位、版本或抓取时间、相关片段及内容指纹 |

`doc` 与 `file/git` 可以组合：前者表示证据语义，后者说明保存和定位方式。

**证据门槛应从「存在 sources」改为「来源支持该主张」。** 例如：

- 版本命令成功，只能证明当时那个可执行文件的版本。
- 用户确认技术路线，不能证明实现已完成。
- 文档写着测试通过，首先证明的是「文档有此声明」，不能直接登记为本次执行通过。

保存命令来源也不能让 Controller 自动重跑命令；重新执行仍受当前授权约束，记录用户曾经授权也不能使授权永久有效。

### C. 外发策略与 A/B 基线 —— 认同，两者均应前置

按目标分级是正确方向，但目标名称还不够，应同时区分**数据类别、账户或工作区、供应商端点、用途及留存条件**。本地模型仅在确认不会转发或上传时才能视为本地处理；云端 Codex、GPT 会话、模型 API 和 Obsidian Sync 都应是独立外发目标。**批准某次候选提取，不等于批准把同一资料交给其他服务评测。**

**Phase 1 可先验收「外发阻断 + 载荷预览」，不必真实外发。** 未来审批应绑定实际脱敏载荷、目标、用途和预算。

A/B 应先固定基线，但不需要为了基线清理现有 EQDM 工作区。建议固定：

1. 来源提交及必要的工作区快照哈希；
2. Vault 版本和检索规则；
3. 原生 Memories 的实际设置；无法确认时明确列为混杂因素；
4. 模型、提示、工具权限、题目、评分规则及时间窗口；
5. 对照组与实验组的独立会话，防止相互污染。

只评估检索质量，不要求先执行 EQDM 全量测试；若声称提升了代码正确率或任务完成率，就必须加入相应执行验证。**云端 A/B 自身属于外发，需要单独批准。**

## 四、合并后的 Phase 1 边界（待用户确认）

**定位升级：** 从「能存取记忆」升级为「**能按来源证明、按批准版本检索、按项目隔离，并在未获授权时阻断外发**」。

**建议验收点：**

- 未审核内容永不进入默认检索；
- 每条记忆可追溯到类型匹配的来源证据；
- 索引可从正式记忆重建；
- 同一份正式记忆的上下文输出不依赖任何单一 Agent 的私有状态；
- 未获授权时外发被阻断，载荷预览可按目标展示。

**Phase 1 不做：** 真实云模型调用、自动外发、后台调度、Git Hook、实时任务状态管理、自动批准记忆、自动开发 Loop、修改 Agent 全局配置。
